# コメント削除後の検索条件・一覧維持の修正（2026-10-18）

## 原因

develop上の未コミット変更を確認して保持した。コメント削除処理自体は対象課題のcommentsだけを置換し、GETを呼んでいなかった。しかし、以下の処理が連動して一覧を絞り込んでいた。

1. 行選択のreplaceUrlが検索用scheduleIdを選択行のscheduleIdで上書きし、scheduleDateNo・traineeEmployeeIdもURLへ保存していた。
2. 削除確認ダイアログから戻った際などのfocusで、AuthProviderが認証を再確認する。同一社員でも新しいuserオブジェクトが設定される。
3. ProgressPageの初期取得useEffectがuserオブジェクトに依存していたため再実行された。
4. URLから検索フォームを再構築し、選択用の日付・提出者まで検索APIへ渡した。その結果「すべて」が選択スケジュールに変わり、一覧が選択課題だけになった。

フォーム編集中の値と実際に検索済みの値も区別されていなかった。

## 最小限の修正

- 選択課題のスケジュールはselectedScheduleIdへ保存し、検索用scheduleIdを上書きしない。
- 初期取得はユーザーオブジェクトではなく社員ID・社員区分・認証待機状態に依存させる。同一社員の認証再確認で一覧を初期化しない。認証失効や別社員への切り替えは既存認証機構に従う。
- 入力中のformと検索実行時のappliedFiltersを分離する。行選択・詳細を閉じる・エラー再取得は適用済み条件を使う。
- 新しい選択URLを再読み込みしても、選択情報を検索APIの絞り込み条件にしない。旧HomeリンクのscheduleId・scheduleDateNo等は既存どおり解釈する。
- コメント登録・編集・削除、ステータス・レビュー者更新のAPIや更新処理は変更しない。コメント削除では対象コメントだけを画面から除く。

API仕様・DB構造・Flyway・認可・画面デザインの変更はない。
