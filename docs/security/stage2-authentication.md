# 認証・セッション・HTTPS対策（第2段階）

## ログイン試行制限

現在は単一プロセスを想定し、メモリ内でアカウントと送信元の両方を管理する。パスワード・セッションID・CSRFトークンは保存・ログ出力しない。アカウントキーはDTOで最大10文字、送信元は実接続のremoteAddrを使い、クライアントのForwarded/X-Forwarded-*を直接使用しない。

| 設定（training.portal.login-limit. 以下） | 既定値 | 意味 |
| --- | --- | --- |
| account-attempts | 8 | 300秒内のアカウント別失敗予算。並行認証の予約枠も含む |
| account-window-seconds | 300 | アカウント失敗の時間窓 |
| source-attempts | 200 | 60秒内の送信元別総試行予算。成功・アカウント制限中の試行も対象 |
| source-window-seconds | 60 | 送信元総試行の時間窓 |
| block-seconds | 60 | 失敗上限到達または送信元上限超過後の一時停止。拒否を繰り返しても延長しない |
| max-keys | 10000 | アカウント・送信元それぞれの最大記録件数 |
| max-concurrent | 32 | サーバー全体の同時認証上限 |

各設定はapplication.propertiesに記載したTRAINING_PORTAL_LOGIN_*環境変数で変更可能。時間は単調時計で測り、同じアカウントの成功は失敗回数をリセットする。送信元の総試行は成功でも消費する。ロック期限後に新しい予算で再試行できる。実行中の認証は期限経過でも記録から消さず、予約・カウンタ変更を同期して並列回避を抑止する。

上限・容量・実行中予約により受付できない場合は429 LOGIN_RATE_LIMITEDとRetry-After秒数を返す。容量・同時実行枠の不足時は1秒後の再試行案内。認証失敗は従来の401 LOGIN_FAILED、CSRF違反は従来の403であり、CSRF検証前に認証処理を実行しない。既知・未知IDを同じルールで扱うが、ネットワークやDB等のタイミング差まで一定にするものではない。

これらは初期運用値で、負荷測定に基づく最適値ではない。共有IP/NATでは正常な利用者も送信元上限を共有する。短い停止と設定可能な予算で影響を限定し、運用前に調整する。再起動で状態は消失する。複数プロセス/複数サーバーでは共有ストアによる原子的な予約・失敗・期限管理が必要で、現実装を各ノードへ配るだけでは制限を保証できない。分散DoS、CSRF取得によるセッション大量生成、通信帯域・リクエスト本文量の制限は別の運用対策が必要。

## パスワード変更

非空のパスワード更新時に既存auth_versionを増加させる。同じ平文を再設定した場合も変更操作として失効させる。空欄は従来どおり変更なし。氏名だけの変更では増加しない。区分とパスワードを両方変更すれば世代がそれぞれ増加するが、いずれも旧世代を拒否する目的は同じ。

既存のRoleSessionGuardは次回APIで旧世代を401として拒否し、古いブラウザのセッションも破棄する。ログイン時のセッションID・CSRF更新は維持。更新カウンタの競合は409であり、失敗したトランザクションの世代更新・パスワードは保存しない。認証済みAPIの更新は既存のDB共有ロック下で確認し、変更後に待機中の旧世代の更新を通さない。既に認可済みで実行中の読み取り応答まで取り消すものではない。

自分のパスワード変更はPUT成功後に既存のrefreshUserを呼び、401を受けてログインへ戻る。管理者が他人のパスワードを変更しても、管理者自身のセッションは維持する。氏名のみの更新も維持。既存UIの構成・デザインは変更しない。

## 本番HTTPS

prodプロファイルでrequire-https、Secure、HttpOnlyを必須とし、SameSiteはLaxを維持する。HTTPリクエストは認証・CSRFセッション生成より前に403 HTTPS_REQUIREDで拒否する。HTTPからのHTTPSへの自動リダイレクトは行わず、Hostヘッダーで外部URLを組み立てない。

server.forward-headers-strategy=noneを採用し、prodでnative/frameworkへ変更すると起動を拒否する。未確定のプロキシを信頼する危険を避けるためであり、X-Forwarded-ProtoだけではHTTPをHTTPSとして扱わない。ローカルのHTTP開発・既存テストはprodを有効にしないことで継続できる。

[直接TLS用の設定例](templates/application-prod-tls.properties.example)を利用先で複製し、Spring Bootの追加設定として読み込む。これは未記入のテンプレートであり、鍵・証明書を含まない。prodだけを有効にしてもTLSリスナーが自動的に構築されるわけではない。TLS未設定ならHTTPは拒否され、ログインできない。

リバースプロキシを使う場合は、現段階ではバックエンドまでTLSを維持する構成のみを想定する。プロキシでTLSを終端しバックエンドへHTTPで渡す構成は未対応。将来対応する場合は、信頼するプロキシアドレスの限定、外部からのバックエンド直通遮断、転送ヘッダーの上書き・検証、実IPと試行制限の関係を決めてから変更・テストする。広い信頼範囲や無条件の転送ヘッダー採用で回避しない。

証明書・ドメイン・リバースプロキシ製品・外部HTTP遮断・TLS終端方式は未決。フロントNext.js側のHTTPSやCookieを扱う実ドメイン、HSTS、証明書更新、鍵保管も別途運用確認が必要。アプリの設定だけで外部ネットワークのHTTP遮断やTLS終端が保証されたと扱わない。

## 設計書への追記対象

基本詳細設計書のログイン・認証エラー（429/待機解除）とメンバー更新イベント（パスワード変更後の再認証）、運用設計のprod/TLS/プロキシ信頼境界へ反映が必要。テーブル定義書のauth_version説明へ、区分変更に加えてパスワード変更で増加することを追記する。DB構造は変更しない。Excelは今回編集していない。

フロントとAPIが別サイトとなるURL構成では、既存のSameSite=LaxによりCookieが送信されない場合がある。同一サイト構成を含め本番URLを確定して再検証する。便宜的にSameSite=Noneや許可Originのワイルドカードへ変更しない。アカウント別の一時停止は第三者によって誘発される可能性があるため、運用時には頻度・共有IPの影響を監視し、必要ならMFAや安全な遅延方式を検討する。
